# Детекция рук: слой признаков для переноса на робота

Зачем это заводилось. Разметка действий отвечает на вопрос «что произошло» и описана
контрактом кейсодателя — границы, действие, предмет, ключевой кадр. Для обучения робота
этого мало: нужно, **как** двигалась кисть. Поэтому руки живут отдельным слоем рядом с
разметкой, контракт не трогают, и целятся не в метрику кейса, а в перенос движения на
кисть вроде Inspire RH56.

Побочно проверялась и вторая гипотеза — что признаки рук помогут самой языковой модели
называть действия. Она не подтвердилась, и это описано ниже честно.

---

## 1. Что построено

| файл | что делает |
| --- | --- |
| `scripts/serve_hands.py` | детектор на **MediaPipe**, CPU, 8 МБ. Ручки `/pose` (поза кистей) и `/focus` (пометка кадров) |
| `scripts/serve_hands_wilor.py` | детектор на **WiLoR** (CVPR 2025), GPU. Тот же контракт `/pose` |
| `scripts/hand_features.py` | слой разметки: поза на каждый кадр плюс сводка на каждый шаг |
| `scripts/hand_video.py` | рендер: скелет поверх кадра, полоса шагов, кривые раскрытия и скорости |

Два детектора отдают **один и тот же формат**, поэтому `hand_features.py` и
`hand_video.py` работают с любым — меняется только `--url`. Это оказалось важно: сравнить
модели удалось без единой правки клиента.

### Формат слоя

Файл на ролик, рядом с разметкой действий, не внутри неё:

```json
{
  "clip": "test_bottle", "fps": 8.0, "duration_sec": 30.2,
  "model": "wilor-mini (WiLoR, CVPR 2025)",
  "frames": [
    {"t": 0.0, "hands": [{
        "side": "Right", "score": 0.41,
        "landmarks": [[x, y, z], ...],   // 21 сустав в долях кадра — где рука в сцене
        "world":     [[x, y, z], ...],   // 21 сустав в метрах — какая это поза
        "aperture": 0.087, "spread": 0.149
    }]}
  ],
  "steps": [{"id": 0, "start_sec": 0.2, "end_sec": 3.2, "action": "put down",
             "hands_seen": 1.0, "wrist_path": 0.86, "wrist_speed": 0.19,
             "aperture_min": 0.019, "aperture_max": 0.057}]
}
```

Метрические координаты — главное, ради чего всё делалось: их ждёт ретаргетинг. Он работает
с **векторами между суставами**, а не с пикселями, поэтому переносится на чужую кинематику.

Производные величины (раскрытие, разброс, путь запястья) считает клиент, а не сервис:
сервис намеренно без памяти о ролике — он отвечает про кадр, а «за шаг раскрытие сузилось»
это уже про последовательность.

## 2. Где детектор видит руки, а где нет

MediaPipe, все 30 роликов валидации, доля кадров **хотя бы с одной** кистью:

| набор | роликов | медиана | худший ролик |
| --- | --- | --- | --- |
| assembly101-coarse | 8 | 99 % | 83 % |
| assembly101-fine | 10 | 100 % | 69 % |
| epic-kitchens | 4 | 53 % | 51 % |
| charades | 8 | **12 %** | **0 %** |
| filmed (ролики кейсодателя) | 3 | **97–100 %** | — |

**Домен кейса закрыт полностью**: настольная манипуляция со статичной камерой — 97–100 %.
EPIC проваливается структурно (эгоцентрика, кисть уходит за край кадра), Charades почти
пуст (человек в глубине комнаты, кисть занимает десятки пикселей).

### Но «есть руки» ≠ «есть обе»

Число кистей на кадр, MediaPipe:

| набор | 0 рук | 1 рука | 2 руки |
| --- | --- | --- | --- |
| assembly101-fine | 4 % | **58 %** | 37 % |
| assembly101-coarse | 3 % | 53 % | 44 % |
| epic-kitchens | 45 % | 41 % | 13 % |
| charades | 76 % | 17 % | 7 % |

На Assembly в большинстве кадров находится **только одна** кисть, хотя работают почти
всегда двумя: вторая держит предмет снизу и частично перекрыта первой. Мигание при этом
редкое (40 кадров из 1410 на fine) — то есть это не дрожание детекции, а устойчивая потеря
второй руки на длинных отрезках.

## 3. WiLoR вместо MediaPipe

Именно потерянная вторая рука и заставила искать модель посильнее. WiLoR устроен под эту
задачу: сначала свёрточный детектор находит кисти, потом трансформер восстанавливает позу.

Доля кадров **с двумя** руками на одних и тех же роликах:

| ролик | MediaPipe | WiLoR |
| --- | --- | --- |
| assembly fine 9013 | 40 % | **82 %** |
| assembly fine 9011 | 58 % | **80 %** |
| assembly coarse b08a | 56 % | **74 %** |
| **epic P01_11_52** | 2 % | **45 %** |
| **charades 5A9O4** | 15 % | **55 %** |
| charades 1BGZ0 | 0 % | 1 % |

На EPIC рост в двадцать раз. Не помогает только там, где информации в кадре нет вовсе
(`1BGZ0` — человек в глубине комнаты).

Цена: **71 мс на кадр на карте** против 40 мс у MediaPipe на процессоре, то есть вдвое
дороже и требует GPU. Но всё ещё быстрее реального времени: ролик в 30 секунд при 8 к/с
обрабатывается за 17.

WiLoR отдаёт больше: **параметры MANO** (`global_orient`, `hand_pose`, `betas`), меш кисти
и положение в камере (`pred_cam_t_full`). MediaPipe даёт только точки.

Два подводных камня, оба обойдены в коде:

* **Ложная третья рука** примерно на 7 % кадров, обычно на смазанных участках. Отсекается
  по площади рамки — в кадре один человек, и это допущение записано явно.
* **Уверенности WiLoR наружу не отдаёт.** В поле `score` кладётся доля кадра, занятая
  рамкой: сравнивать кисти между собой она позволяет, выдавать за вероятность — нет.

## 4. Что не сработало: руки как подсказка языковой модели

Проверялись три способа, все замерены на 142 шагах валидации.

### Пометка кадров

| способ | что делает | предмет по всем шагам |
| --- | --- | --- |
| без пометки | — | 0.176 |
| обводка красным овалом | сцена цела, зона обведена | 0.169 |
| скелет поверх кадра | линии по суставам | **обвал**: на fine предмет 0.149 → **0.011** |

Скелет физически закрывает ту самую мелкую деталь в руке, которую надо назвать. Обводка
нейтральна к предмету, но вредит там, где детекция ненадёжна: на EPIC и Charades качество
падает, потому что при потерянной руке овал наследуется с прошлого кадра и указывает не
туда. **Неверная пометка хуже, чем никакой.**

### Признаки текстом

В промпт добавлялась строка вида «правая кисть, раскрытие 5.8 → 3.8 см, запястье прошло
0.52 доли кадра». Гипотеза строилась на замере: «взял» = кисть **закрывается**, «положил»
= **раскрывается**.

| эталон | шагов | закрывается | раскрывается |
| --- | --- | --- | --- |
| pick up | 11 | **9** | 2 |
| put down | 20 | 9 | 11 |

Половина гипотезы верна, вторая — монета. Результат ровно такой:

| набор | без подсказки | с подсказкой |
| --- | --- | --- |
| assembly101-fine | 0.230 / 0.264 | 0.253 / 0.276 |
| epic-kitchens | 0.474 / 0.579 | 0.474 / 0.579 |
| charades | 0.211 / 0.316 | 0.211 / 0.316 |
| assembly101-coarse | **0.294 / 0.529** | 0.118 / 0.412 |

Исправлено 6 шагов, испорчено 5, инверсий «взял/положил» стало **больше** (1 → 3): модель
послушно следует подсказке там, где та врёт. На EPIC и Charades числа не изменились вовсе —
детектор там теряет руки, и строка в промпт не уходит.

**Вывод:** как данные для робота руки работают, как подсказка модели — нет. Обе ручки
выключены по умолчанию (`PRAXIS_HANDS_NOTE=0`, `PRAXIS_HANDS_MODE=none`).

Если возвращаться, менять надо сам признак: не усреднённое раскрытие по третям, а **момент
смены знака** внутри шага — усреднение стирает разницу между «опустил и отпустил» и
«опустил и держит».

## 5. Ретаргетинг на робота: что проверено

`dex_retargeting` (MIT, из системы AnyTeleop) переводит движение кисти в углы суставов
робота. **Inspire есть в поставке**: `configs/offline/inspire_hand_right.yml`, тип
`position` — тот, что предназначен для постобработки человеческих данных под имитационное
обучение. URDF берётся из `dex-urdf`.

Конфиг ждёт человеческие индексы `[4, 8, 12, 16, 20]` — кончики пальцев в схеме MediaPipe.
Порядок суставов у WiLoR проверен **по длинам костей**: под этой схемой у обоих детекторов
получается анатомически осмысленный скелет (ладонные кости 8–10 см, фаланги 2–4 см). Первая
попытка сверить порядок сопоставлением точек в 2D оказалась негодной — пальцы прижаты друг
к другу, ближайший сосед путает соседние суставы.

На настоящем кадре получено 18 чисел: шесть вспомогательных (положение и поворот кисти) и
углы приводов. Пальцы согнуты примерно наполовину от предела — правдоподобно для кисти,
держащей деталь.

Что осталось до воспроизведения в симуляторе:

* **приведение к MANO** — сдвиг в запястье, поворот по точкам 0-5-9, матрица `OPERATOR2MANO`;
  без него поза робота зависит от того, как рука повёрнута к камере;
* **частота** — 8 к/с мало для гладкого проигрывания, нужна интерполяция;
* **пропуски** — кадры без рук оставляют дыры; их надо помечать, а не заполнять: робот не
  должен повторять то, чего мы не видели;
* **дрожание** — `low_pass_alpha: 1` отключает фильтр, покадровое дрожание пойдёт в привод;
* **запястье в сцене** — вспомогательные шесть чисел живут в системе координат MANO, а не
  в метрах сцены; для переноса предмета нужен `pred_cam_t_full` от WiLoR.

## 6. Как запускать

```bash
# детектор на CPU (MediaPipe), порт 8105
CUDA_VISIBLE_DEVICES="" python scripts/serve_hands.py --port 8105 \
    --model models/hand_landmarker.task

# детектор на карте (WiLoR), порт 8106 — отдельное окружение
CUDA_VISIBLE_DEVICES=1 /venv/wilor/bin/python scripts/serve_hands_wilor.py --port 8106

# слой рук по папке роликов, привязанный к нашей же разметке
python scripts/hand_features.py --clips клипы/ --steps-dir разметка/ \
    --out-dir work/hands/ --url http://127.0.0.1:8106

# рендер для глазной проверки
python scripts/hand_video.py --clip ролик.mp4 --hands work/hands/ролик.json --out demo.mp4
```

Веса MediaPipe (8 МБ) качаются с сайта Google:

```bash
curl -L -o models/hand_landmarker.task \
  https://storage.googleapis.com/mediapipe-models/hand_landmarker/hand_landmarker/float16/1/hand_landmarker.task
```

### Установка WiLoR: три грабли подряд

1. **Python 3.10, не 3.12.** Зависимость `chumpy` (от MANO) использует `inspect.getargspec`,
   которого в 3.12 больше нет. Окружение создаётся через mamba.
2. **`chumpy` ставится из git**, а не из PyPI: в опубликованной версии `setup.py` импортирует
   сам pip, которого нет в изолированной сборке. Помогает
   `pip install --no-build-isolation git+https://github.com/mattloper/chumpy`.
3. **`dill` доустанавливается вручную** — без него не читаются веса детектора YOLO внутри
   WiLoR.

## 7. Настройки

| переменная | по умолчанию | что делает |
| --- | --- | --- |
| `PRAXIS_HANDS_BASE_URL` | пусто | адрес детектора; пусто — слой не считается |
| `PRAXIS_HANDS_MODE` | `white` | пометка кадров: `none`, `white`, `circle`, `skeleton` |
| `PRAXIS_HANDS_NOTE` | `0` | отдавать ли признаки кисти текстом в промпт |
| `PRAXIS_HANDS_MARGIN` | `1.5` | запас вокруг кисти долями её размера |
| `PRAXIS_HANDS_MIN_RADIUS` | `0.12` | нижняя граница радиуса долей кадра |

Замеры выше получены при `--fps 8` и ширине кадра 1280 для детектора: на уменьшенной
картинке MediaPipe теряет кисть, которая занимает около полутора процентов площади.
