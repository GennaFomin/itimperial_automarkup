# Слой `/api/v1`: что реализовано и где расходится с контрактом

Контракт из [`contracts.md`](../contracts.md) описывает, как нас принимают снаружи.
Внутренняя модель praxis богаче: у неё иерархия шагов, отметка проверки человеком и
происхождение прогона. Обеднять её ради внешней формы неправильно, поэтому контракт
живёт рядом — как проекция, а не вместо.

Реализация: [`praxis/api_v1.py`](../praxis/api_v1.py) — маршруты,
[`praxis/contract_v1.py`](../praxis/contract_v1.py) — конверсия (чистые функции, тесты
без HTTP), [`praxis/errors.py`](../praxis/errors.py) — коды.

Внутренний `/api/videos/*` не изменился ни в одном ответе: на нём стоят собственные
тесты, и ломать их ради внешней формы не было причины.

---

## Единицы и идентификаторы

| Контракт | Внутри | Как переводится |
|---|---|---|
| `start_ms`, `end_ms`, `keyframe_ms` — целые мс | `*_sec` — секунды, float | `round(sec * 1000)`, обратно `ms / 1000` |
| `id: "seg_001"` | `id: int` | `f"seg_{id:03d}"`, обратно разбором |
| `object.value: "unknown"` | `object: None` | пара симметричных конверсий |
| `origin: model \| human` | `source: auto \| edited \| manual` | `source` вычисляется, а не принимается от клиента |

**Округление не должно выглядеть правкой.** Граница `5.10049` уходит как `5100` мс и
вернулась бы как `5.100`. Без защиты `diff_steps` засчитал бы сдвиг границы там, где
человек ничего не трогал, и телеметрия правок — та, на которой строится KPI
«в три раза быстрее», — начала бы завышать работу человека. Поэтому при обратной
конверсии значение, отличающееся меньше чем на полмиллисекунды, берётся из базы
дословно. Проверяется тестом `test_round_trip_on_ragged_times_is_not_an_edit`; парный
тест следит, чтобы защита не проглатывала настоящую правку.

**Конец клампится по длительности:** `round(19.9996 * 1000)` даёт 20000 при ролике в
19999 мс, а это нарушение инварианта §3.1.

## Уверенности: почему половина полей `null`

Контракт (§1) требует confidence по полям — отдельно для границы, действия, объекта и
ключевого кадра. Пайплайн производит **одно** число на шаг, и это уверенность
**именования пары** «действие + объект».

| Поле контракта | Что отдаём | Почему |
|---|---|---|
| `action.confidence` | `Step.confidence` | единственное место, где число что-то значит |
| `object.confidence` | `null` | то же число во втором поле выдало бы зависимую величину за независимую |
| `boundary_confidence` | `null` | разрез — это выброс в ядровой статистике, а не вероятность |
| `keyframe_confidence` | `null` | у всех сегментаторов, кроме `motion-dp`, кадр — середина отрезка |

Ничего из этого не заполняется суррогатом: константа вроде `0.5` выглядит как
измерение и молча портит и разметку, и доверие к метрике. Тест
`test_missing_confidences_are_null_not_invented` существует именно для того, чтобы
эти поля не «починили».

Чтобы `null` не читался как недоделка, ответ `prediction` несёт блок `capabilities`:

```json
"capabilities": {
  "boundary_confidence": false,
  "object_confidence": false,
  "keyframe_confidence": false,
  "action_confidence": "pair",
  "keyframe_source": "midpoint",
  "open_vocabulary": true
}
```

**Открытый пункт.** У `EnsembleSegmenter` есть доля согласия методов на разрезе — это
настоящий сигнал для `boundary_confidence`. Его стоит вывести наружу, когда ансамбль
станет режимом по умолчанию.

## Статусы и стадии

| Контракт | Внутри | |
|---|---|---|
| `queued` | `queued` | |
| `running` | `processing` | переименование |
| `done` | `done` при пустых `warnings` | |
| `done_with_errors` | `done` при непустых `warnings` | прогон прошёл не в полную силу: сервис признаков или именования был недоступен |
| `failed` | `failed` | `error.code` выводится из текста: `MODEL_TIMEOUT`, `DECODE_FAILED` или честный `INTERNAL` |
| `cancelled` | `cancelled` | реализовано |

`warnings` разворачиваются в контрактный `errors[]` с кодом `DEGRADED`. Сегменты без
ключевого кадра дают отдельную запись со стадией `keyframe` и списком `segment_ids`.

**Стадии.** Контракт называет пять: `decode · proposals · recognize · keyframe ·
validate`. Пайплайн проходит три — `decode`, `recognize` (сегментация и именование
слиты в одну стадию), `validate`. `proposals` и `keyframe` не эмитируются никогда:
показывать их пройденными означало бы рисовать прогресс, которого нет.

**Отмена.** Фоновую задачу нельзя убить извне, но `jobs.process_video` проходит через
`checkpoint()` между стадиями — там и проверяется флаг `cancel_requested`. Отмена
срабатывает на ближайшей границе стадии, начатая стадия доигрывает. Повторная отмена
и отмена завершённого задания — не ошибка (§2 требует идемпотентности).

## Словарь

Внутренний словарь — плоский список строк без оформления, а при
`PRAXIS_OPEN_VOCABULARY=1` классы вообще не известны заранее. Слой достраивает форму §6:

- `id` — сама строка словаря, дословно: она обязана вернуться в `Step.action` без
  изменений, иначе проверка по словарю начнёт ругаться на собственный словарь;
- `label_ru` — из необязательной карты `labels` в YAML, иначе сам `id`. Машинного
  перевода нет намеренно: при открытой лексике модель отвечает на языке
  `PRAXIS_LANGUAGE`, и её ответ уже является подписью;
- `color` — детерминированно из названия (хеш → тон HSL с фиксированными
  насыщенностью и светлотой). Один и тот же класс всегда одного цвета: в таймлайне, на
  скриншоте, после перезагрузки и на другой машине. Новый класс не требует правки YAML —
  что при открытой лексике обязательно;
- `unknown` дописывается в оба списка: контракт знает его как значение, а пайплайн
  кодирует отсутствие объекта через `null`;
- флаг `open` говорит клиенту, что список — подсказка, а не ограничение.

## Расширения

Всё аддитивно: по §1 клиент игнорирует незнакомые поля.

**Поля.** В теле правки — `verified_ids[]` (какие сегменты человек подтвердил глазами)
и `mode: review | scratch`. В ответах — `capabilities`, `problems[]`, `id_map`
(временный идентификатор клиента → присвоенный).

**Эндпоинты.** `GET /jobs` — список для экрана задач одним запросом вместо N.
`GET /limits` — ограничения на вход прямо из конфигурации, чтобы смена лимита не
требовала релиза фронта. `GET /stats` и `POST /jobs/{id}/activity` — замер времени.
`GET /jobs/{id}/media` и `/frame?ms=` — видео и кадр по времени.

**Коды.** `VIDEO_TOO_SMALL` (кейс требует не ниже 720p), `INVALID_REVIEW`, `DEGRADED`.

## Время работы человека

`GET /stats` считает `speedup` из двух рядов событий: `review_seconds` и
`scratch_seconds`. Оба пишет **только** `POST /jobs/{id}/activity` — таймер шлёт
дельты активных секунд по ходу работы.

Поле `time_spent_ms` из отправки правки в этот счётчик **не попадает**: оно
сохраняется в журнале как `wall_ms`, время по часам. Сложить оба замера означало бы
посчитать один и тот же интервал дважды и превратить `speedup` в мусор. Тест
`test_submit_does_not_double_count_time` закрепляет это.

Замер разметки с нуля (`mode: "scratch"`) намеренно **не сохраняется** поверх
настоящей правки: иначе очищенная для замера дорожка стёрла бы работу человека.

## Чего в контракте нет и не будет здесь

- `POST /jobs` принимает только загрузку файла. Ссылки на внешнее хранилище пайплайн
  не качает — открытый вопрос №2 контракта ещё не решён.
- `options.vocab_version` и `options.max_segments` не поддерживаются: гранулярность
  задаётся конфигурацией прогона, а не запросом.
- `stats.frames_decoded` не отдаётся: у пайплайна нет одного числа, которое означало бы
  ровно это. `stats` несёт `latency_ms`, `cost` и разбивку `stages_ms`.
- `cost` вместо `cost_usd`: сумма считается по ставке `PRAXIS_GPU_HOUR_COST`, валюта
  которой не обязана быть долларом. Поле стоит согласовать с владельцем контракта.
